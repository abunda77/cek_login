# PRD: Linux SSH Security Analyzer

## 1. Project Overview

Build a **read-only Linux SSH security analysis CLI tool in Python**.

The tool collects authentication and session information from a Linux server using existing CLI commands, performs deterministic rule-based analysis, then sends the collected evidence and rule-based findings to an **OpenAI-compatible LLM API**.

The LLM must:

1. Correlate events from multiple sources.
2. Identify suspicious authentication patterns.
3. Assess security severity.
4. Explain the reasoning using concrete evidence.
5. Produce a concise conclusion.
6. Recommend remediation actions.

The tool must **never automatically modify the Linux system**.

Examples of prohibited automatic actions:

- modifying SSH configuration;
- blocking IP addresses;
- running `iptables`, `nft`, `ufw`, or `fail2ban` commands;
- killing processes;
- disabling users;
- restarting services;
- deleting files;
- changing passwords;
- modifying firewall rules.

The application is an **analysis and reporting tool only**.

---

# 2. Goals

## Primary Goals

- Analyze Linux SSH authentication activity.
- Detect brute-force behavior.
- Detect repeated attacks against privileged accounts.
- Detect suspicious successful logins.
- Correlate failed and successful authentication events.
- Identify currently active sessions.
- Identify suspicious source IP addresses.
- Provide severity and confidence.
- Generate actionable remediation recommendations.
- Support multiple OpenAI-compatible providers without changing application code.
- Work from the Linux CLI.
- Provide both human-readable and machine-readable output.

## Secondary Goals

- Preserve the raw evidence.
- Make all findings traceable to evidence.
- Allow future collectors to be added without changing the analyzer architecture.
- Allow local/self-hosted LLM inference.

---

# 3. Non-Goals

The MVP must NOT implement:

- automatic IP blocking;
- automatic SSH hardening;
- automatic firewall configuration;
- malware scanning;
- vulnerability scanning;
- port scanning;
- intrusion prevention;
- SIEM integration;
- email notifications;
- Slack/Telegram notifications;
- database persistence;
- web dashboard;
- automatic remediation;
- autonomous shell commands generated by the LLM.

These features may be introduced later as separate modules.

# 5. Security Model

The application must operate in **read-only mode**.

The Python process may execute only predefined collector commands.

The LLM has no shell access.

Never construct shell commands from LLM output.

Never execute model-generated commands.

Never pass arbitrary user-provided strings directly into shell command construction.

Use `subprocess.run(..., shell=False)` wherever possible.

Commands must be represented as argument arrays.

Example:

```python
[
    "last",
    "-a",
    "-n",
    "100"
]
```

instead of:

```python
"last -a -n 100"
```

# 7. Collector Architecture

Use a common collector interface.

Example:

```python
from abc import ABC, abstractmethod

class Collector(ABC):

    name: str

    @abstractmethod
    def collect(self) -> "CollectorResult":
        pass
```

Each collector returns a common structure.

Example:

```python
@dataclass
class CollectorResult:
    collector: str
    command: list[str]
    status: str
    exit_code: int | None
    stdout: str
    stderr: str
    duration_ms: int
    collected_at: str
```

Possible status values:

```text
success
command_not_found
permission_denied
execution_error
timeout
empty
```

# 12. Deterministic Rule Engine

Before calling the LLM, run rule-based analysis.

The rule engine must detect at minimum:

## Rule R001: Repeated Failed Login

Trigger when:

```text
same IP >= 5 failed authentication attempts
```

Severity:

```text
LOW
```

---

## Rule R002: High-Volume Failed Login

Trigger when:

```text
same IP >= 20 failed authentication attempts
```

Severity:

```text
MEDIUM
```

---

## Rule R003: Aggressive Brute Force

Trigger when:

```text
same IP >= 50 failed authentication attempts
```

Severity:

```text
HIGH
```

---

## Rule R004: Root Targeting

Trigger when:

```text
username == root
```

and there are repeated failed attempts.

Severity:

```text
MEDIUM
```

Increase severity by one level if the volume is high.

---

## Rule R005: Multiple User Targeting

Trigger when:

```text
same IP attacks multiple usernames
```

Possible classification:

```text
password_spraying_or_account_enumeration
```

Severity:

```text
MEDIUM
```

---

## Rule R006: Successful Login After Repeated Failures

Trigger when:

```text
same IP has repeated failed logins
AND
same IP later has successful login
```

Severity:

```text
HIGH
```

This is one of the most important correlation rules.

---

## Rule R007: Suspicious Current Session

Trigger when:

```text
current session source IP
```

matches an IP associated with suspicious authentication activity.

Severity:

```text
HIGH
```

Do not claim compromise automatically.

Use wording such as:

```text
"Potentially suspicious active session"
```

---

## Rule R008: Multiple Remote Sources

Detect successful logins from multiple remote IP addresses within a short period.

This is contextual evidence, not automatically malicious behavior.

# 13. Risk Scoring

Implement a deterministic score.

Initial scoring:

```text
Failed attempts 5-19       +10
Failed attempts 20-49      +20
Failed attempts >=50       +30
Root targeted              +15
Multiple usernames         +15
Success after failures     +30
Suspicious active session  +30
Multiple remote sources    +10
```

Cap score:

```text
100
```

Mapping:

```text
0-19    INFO
20-39   LOW
40-59   MEDIUM
60-79   HIGH
80-100  CRITICAL
```

The LLM may interpret the score but must not silently replace it.

The final report must distinguish:

```text
deterministic_score
llm_assessment
final_severity
```

# 17. LLM Prompt Requirements

Create:

```text
prompts/security_analysis.txt
```

The system prompt should instruct the LLM:

```text
You are a Linux security analyst.

You are analyzing authentication and session evidence collected from a Linux server.

Your task is to:

1. Correlate events from different sources.
2. Identify suspicious authentication behavior.
3. Distinguish facts from hypotheses.
4. Never invent evidence.
5. Never claim a system is compromised without sufficient evidence.
6. Reference concrete usernames, IP addresses, timestamps, and event counts when available.
7. Explain why an activity is suspicious.
8. Provide prioritized remediation recommendations.
9. Clearly identify uncertainty.
```

# 19. Pydantic Validation

Use Pydantic to validate LLM output.

Example models:

```python
class EvidenceRef(BaseModel):
    source: str
    ip: str | None = None
    count: int | None = None

class Finding(BaseModel):
    title: str
    severity: Literal[
        "INFO",
        "LOW",
        "MEDIUM",
        "HIGH",
        "CRITICAL",
    ]
    confidence: float
    description: str
    evidence: list[EvidenceRef]

class Correlation(BaseModel):
    description: str
    risk: str

class Recommendation(BaseModel):
    priority: int
    action: str
    reason: str

class SecurityReport(BaseModel):
    severity: Literal[
        "INFO",
        "LOW",
        "MEDIUM",
        "HIGH",
        "CRITICAL",
    ]
    confidence: float
    summary: str
    findings: list[Finding]
    correlations: list[Correlation]
    conclusion: str
    recommendations: list[Recommendation]
    uncertainties: list[str]
```

Reject invalid model output.

Implement one retry with a correction prompt.

If the second attempt fails, return a safe error report instead of crashing.

# 33. Correlation Requirements

The analyzer must correlate:

```text
IP
username
timestamp
event type
collector
```

Important correlations:

### Failed → Successful

```text
failed login
      ↓
same IP
      ↓
successful login
```

### Failed → Current Session

```text
failed login
      ↓
same IP
      ↓
active session
```

### Single IP → Multiple Accounts

```text
IP A
 ├── root
 ├── admin
 ├── ubuntu
 └── test
```

### Multiple IPs → Same Privileged Account

```text
root
 ├── IP A
 ├── IP B
 └── IP C
```

These correlations must be available to both the rule engine and LLM.

# 34. Evidence-Based Language

The generated report must distinguish:

## Fact

```text
37 failed login attempts were observed from IP X.
```

## Strong inference

```text
The pattern is consistent with SSH brute-force activity.
```

## Unverified hypothesis

```text
A successful login following repeated failures may indicate credential compromise, but the available evidence does not prove this.
```

Never produce:

```text
The server has definitely been hacked.
```

unless the evidence actually supports such a conclusion.

---

# 35. Recommendation Requirements

Recommendations must be prioritized.

Categories:

```text
IMMEDIATE
SHORT_TERM
LONG_TERM
```

Examples:

Immediate:

```text
Review suspicious successful authentication.
Review active sessions.
Inspect authentication logs around the event.
```

Short-term:

```text
Enable SSH key authentication.
Disable direct root SSH login where operationally appropriate.
Implement fail2ban or equivalent controls.
Review exposed SSH access.
```

Long-term:

```text
Centralize authentication logs.
Implement alerting.
Establish authentication baselines.
Monitor privileged-account usage.
```

The report must avoid destructive instructions by default.

## Final Severity Resolution

Severity precedence:

CRITICAL > HIGH > MEDIUM > LOW > INFO

The application must maintain three independent values:

- `rule_severity`
- `risk_score`
- `llm_severity`

`final_severity` must be determined from validated evidence.

The LLM cannot arbitrarily escalate severity.

CRITICAL must require evidence of potential successful compromise,
such as:

1. repeated/high-volume authentication failures,
2. followed by a successful login from the same source IP,
3. with an active session from that source IP,

or another explicitly validated equivalent correlation.

Severity values must never be averaged.

When multiple findings exist, the highest validated severity wins.
